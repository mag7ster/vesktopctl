# Эксперимент: восстановление VCC перед перезапуском

Эта самостоятельная версия сохраняет CLI `vesktopctl mute|deafen`, Unix-сокет и нажатие кнопок Discord через JavaScript в главном процессе Vesktop. Она дополнительно возвращает вставку в Vencord перед штатным перезапуском после обновления. Поддерживаемые варианты — Vesktop Flatpak и системные Linux-пакеты. AppImage в этот эксперимент не входит.

## Установка

Нужен Python 3. Сначала запустите Vesktop хотя бы один раз, чтобы он скачал Vencord.

Старая и экспериментальная версии устанавливаются по очереди. Если старая версия установлена, сначала удалите её её же скриптом:

```sh
python3 ~/.local/share/vesktopctl/uninstall.py
```

Установщик эксперимента отказывается работать при обнаружении манифеста старого установщика или старой вставки VCC в bundle. Исходники проекта в родительском каталоге остаются доступными для возврата к старой версии. Пока эксперимент установлен, не запускайте старый установщик: он не умеет обнаруживать эксперимент.

Из корня проекта установите эксперимент:

```sh
python3 experimental-autorepair/install.py --target flatpak
```

Для системного пакета используйте `--target native`. Если Vesktop только один, `--target` можно опустить. Установщик ищет стандартные текущие и старые каталоги, учитывает `$XDG_CONFIG_HOME` и собственную папку Vencord из `state.json`. Для нестандартного пути:

```sh
python3 experimental-autorepair/install.py --target native --bundle /путь/к/vencordDesktopMain.js
```

Установка добавляет CLI в `~/.local/bin` и собственные инструменты в `~/.local/share/vesktopctl-experimental`. Изменённые файлы и исходные настройки сохраняются в `~/.vesktopctl-experimental/` с правами доступа только владельцу. Рядом с bundle создаётся собственный каталог `vesktopctl-experimental` с bridge, кодом восстановления и шаблоном вставки.

Если выбранный Vesktop работает, установщик остановит его перед заменой файлов и запустит после установки. Остановленное им приложение он откроет снова и при ошибке установки. Закрытое приложение он не запускает. Для ручного перезапуска добавьте `--no-restart`; при установке с этой опцией не запускайте параллельно обновление Vencord.

## Команды и Flatpak

```sh
vesktopctl mute
vesktopctl deafen
```

Обе команды переключают состояние. Ответ `OK` означает, что JavaScript нашёл и нажал кнопку; это не подтверждение состояния микрофона от Discord Voice API. Команды выполняются последовательно, ошибки возвращаются через stderr и ненулевой код выхода. Не повторяйте команду автоматически после таймаута: переключение могло уже произойти.

В niri:

```kdl
binds {
    Mod+Shift+M repeat=false { spawn "vesktopctl" "mute"; }
    Mod+Shift+D repeat=false { spawn "vesktopctl" "deafen"; }
}
```

В DMS задайте те же команды. Если `~/.local/bin` отсутствует в `PATH`, используйте полный путь к CLI.

Сокет — `$XDG_RUNTIME_DIR/vesktopctl/control.sock` на хосте. Установщик выдаёт Flatpak только разрешение `--filesystem=xdg-run/vesktopctl:create`. Внутри Flatpak bridge обращается к этому каталогу через `/run/user/<UID>/vesktopctl`; для системного пакета используется `$XDG_RUNTIME_DIR`. Каталог имеет права `0700`, сокет — `0600`. Других разрешений для автовосстановления не требуется: bundle и bridge уже доступны Vesktop в его собственных данных или выбранном Vencord build.

## Как восстанавливается вставка

Загруженный bridge оборачивает `app.relaunch()` и `app.exit()`. Перед исходным вызовом он синхронно читает bundle, проверяет маркеры, компилирует результат через `vm.Script` без выполнения и при необходимости атомарно заменяет файл, сохраняя его права. Для обычного закрытия добавлен обработчик `before-quit`. `app.exit()` также освобождает принадлежащий bridge сокет.

Шаблон `injection.js` общий для Python-установщика и JavaScript-восстановления. Вставка добавляется целиком в конец bundle и включает собственные разделители строк. Повторная проверка не переписывает уже исправный файл. Повреждённые/дублированные маркеры, неверный JavaScript, недоступные файлы и обнаруженная запись другим процессом дают ошибку; исходный вызов Electron всё равно продолжается. Сообщения имеют префикс `[vesktopctl-experimental]` в журнале главного процесса.

Проверка выполняется только при этих вызовах завершения/перезапуска. В простое нет опроса файлов, `fs.watch`, таймера, systemd-службы или внешнего демона. Работоспособность IPC не влияет на регистрацию восстановления. Из sandbox не изменяются Python-манифест и резервные копии установщика.

Основание для этого механизма: [Vencord дожидается записи файлов](https://github.com/Vendicated/Vencord/blob/main/src/main/updater/http.ts), [затем вызывает перезапуск](https://github.com/Vendicated/Vencord/blob/main/src/utils/updater.ts); [Vesktop вызывает `app.relaunch()` и `app.exit()`](https://github.com/Vencord/Vesktop/blob/v1.6.7/src/main/ipc.ts#L68-L81). По [документации Electron](https://www.electronjs.org/docs/latest/api/app#appexitexitcode), `app.exit()` не вызывает `before-quit`, поэтому одного обработчика этого события недостаточно.

Это экспериментальный перехват методов Electron, а не официальный интерфейс расширений updater. Его область — **завершённое штатное обновление Vencord и последующее штатное закрытие или перезапуск**. Он не гарантирует восстановление после SIGKILL, аварии, отключения питания, прерывания записи обновления, перезаписи файлов при закрытом Vesktop или будущей смены схемы загрузки upstream. AppImage может запускать новый процесс до `app.exit()` и поэтому исключён.

Для ручного восстановления после такого случая закройте Vesktop и используйте резервный launcher:

```sh
vesktopctl-vesktop
```

Он применяет вставку один раз перед запуском, без автоматического дополнительного перезапуска. Если Vencord ещё не скачан или проверка завершилась ошибкой, launcher выводит сообщение и всё равно запускает Vesktop. Можно также выполнить `python3 ~/.local/share/vesktopctl-experimental/install.py --patch-only --target flatpak` и затем запустить приложение самостоятельно. Для системного пакета замените target на `native`.

## Удаление и возврат к старой версии

```sh
python3 ~/.local/share/vesktopctl-experimental/uninstall.py
```

Либо выполните `python3 experimental-autorepair/uninstall.py` из исходников. Если Vesktop работает, скрипт сначала остановит его, выполнит откат и запустит снова. Это не даёт загруженному bridge восстановить вставку во время удаления. Опция `--no-restart` требует заранее закрыть Vesktop.

Неизменённые установленные файлы возвращаются из резервных копий. Если Vencord обновился или вставка восстановилась внутри приложения, деинсталлятор удаляет только экспериментальный блок из **текущего** bundle, сохраняя новую версию и её переводы строк. Пользовательские изменения CLI сохраняются с сообщением об ошибке; для повторной попытки можно использовать скрипт из исходников. Flatpak override возвращается целиком, если не менялся; при более поздних изменениях удаляется только добавленное экспериментом разрешение.

После успешного удаления резервные копии и пустые созданные каталоги удаляются. Чтобы вернуть старую реализацию, запустите её установщик из родительского каталога: `python3 install.py`.

## Проверки

Для разработки нужен Node с встроенным `node:test`; npm-пакеты не используются. Из корня проекта:

```sh
node --test experimental-autorepair/tests/*.test.cjs
python3 -B -m unittest discover -s experimental-autorepair/tests -p 'test_*.py' -v
```

Python-тесты используют временные домашние каталоги и имитацию управления процессами/Flatpak. Два теста вызывают настоящий JavaScript-код восстановления: если `node` отсутствует, задайте `VCC_NODE=/путь/к/node`; без runtime эти два теста явно пропускаются. Проверяются завершение обновления, точное удаление вставки, повторная установка, отказ при старом VCC, изменённый CLI, восстановление Flatpak override и управление перезапуском. JavaScript-тесты проверяют атомарную запись, ошибки, последовательность команд и жизненный цикл независимо от сокета.

В модульных тестах объект Electron `app` и транспорт соединения имитируются; операции восстановления выполняются на настоящих временных файлах. Проверка на настоящем Electron и реальном обновлении Discord-профиля выполняется отдельно по следующим сценариям.

Для проверки на настоящем Electron предусмотрен `tests/electron-smoke.cjs`. Запускайте его отдельным **Electron для разработки**, который умеет загружать пользовательские скрипты, с временным профилем:

```sh
VCC_SMOKE_DIR=$(mktemp -d)
export VCC_SMOKE_DIR
electron --no-sandbox --ozone-platform=headless experimental-autorepair/tests/electron-smoke.cjs
```

После выхода в этом каталоге должен быть `vencordDesktopMain.js` с ровно одним экспериментальным блоком и файл `cleaned`. Повторите с новым временным каталогом и `VCC_SMOKE_MODE=quit` для обычного закрытия. Режим `VCC_SMOKE_MODE=relaunch` также запускает дочерний Electron, который проверяет восстановленный bundle и оставляет файл `relaunched`; дождитесь этого файла перед удалением временного каталога. Тест не входит в рабочий Discord-профиль. Упакованный бинарник Vesktop с ограничениями Electron fuses не является готовым test runner.

`tests/electron-ipc-smoke.cjs` проверяет настоящий Unix-сокет, Python CLI и нажатия кнопок JavaScript в скрытом тестовом окне Electron. Для него также задайте новый `VCC_SMOKE_DIR` и запустите скрипт через Electron для разработки. При необходимости используйте `--ozone-platform=x11` вместо `headless`: в проверенном окружении headless завершался аварийно при создании окна. Успешный тест создаёт `ipc-result.json` со счётчиками `mute: "2"`, `deafen: "1"`; после выхода сокет `run/vesktopctl/control.sock` должен отсутствовать, а тестовый bundle должен содержать вставку. Discord и сетевое соединение не требуются.

Вне sandbox подтверждены все 30 модульных/интеграционных тестов без пропусков, восстановление при настоящих `app.exit()`, `app.quit()` и `app.relaunch()`, а также путь CLI → Unix-сокет → renderer на Electron из установленного Vesktop (изолированная временная копия с разрешённой загрузкой тестового приложения). Это не заменяет проверку обновления Vencord в настоящем профиле.

Ручной сценарий проверки установленного эксперимента: вызвать mute/deafen, завершить штатное обновление Vencord, нажать перезапуск в его интерфейсе и снова вызвать CLI без использования резервного launcher. Затем проверить удаление эксперимента. Системную установку автоматические тесты не изменяют.
